# Product work and evidence

Presentation is outside this engineering assessment. Work is confined to VibeCheck; no new paid infrastructure is required.

## Implemented in the verification-depth revision

| Backlog | Implementation | Remaining limit |
| --- | --- | --- |
| 1 — atomic claims | Model extraction plus deterministic splitting of explicit independent predicates; review-before-inspection UI | Ambiguous noun lists, negation and conditional wording need manual review |
| 2 — evidence strength | Parsed package-manifest checks; source-support ceilings for imports, declarations, documentation and broad claims | These are conservative checks, not AST analysis or a semantic proof |
| 3 — retrieval | Up to 16 tree-listed relative import targets after 60 initial candidates; eight explicit source hints; claim-focused source windows with original line numbers and whole-source comment checks | Bounded traversal and 512KB scan cap; no arbitrary alias resolution or whole-repository guarantee |
| 4 — explanations | Expandable checked/established/unknown/next-evidence contract | Model semantics remain fallible |
| 5 — requirements | Normative prose, numbered acceptance items, fenced-code exclusion, exact citations, advisory labels, 32-item cap | Complex tables and implicit requirements remain outside extraction |
| 6 — requirement association | Exact conflict citations take precedence; limited aliases create separately labeled possible matches | Fulfillment is never inferred from shared words or aliases |
| 7 — execution records | Only matching-head GitHub records; name/result/revision attribution without automatic universal certification | A green check cannot establish unspecified tests or runtime behavior |
| 8 — rechecks | Exact-text matching plus explicit user-confirmed equivalence; repository/context/verifier checks | Confirmation is the user's assertion, not verified semantic equivalence |
| 9 — repair handoff | Unresolved claims, cited constraints and acceptance evidence; clipboard and Markdown export | No automatic source modification or assertion that a repair succeeded |
| 10 — recovery | Extracted-claim checkpoint, same-revision recovery, cancellation passed to the provider client, one fallback on SDK-local timeouts | Provider-side computation may continue after client cancellation; six completed evaluation requests do not establish reliable availability |
| 11 — result hierarchy | Conflicts and unsupported claims appear first; details expand on demand | Independent first-use comprehension is unmeasured |
| 12 — more evidence | Select a finding, retain its revision and supply explicit file hints | Hints guide retrieval; they do not establish support |
| 13 — untrusted content | Existing nonce delimiters, literal checks and added support ceilings; deterministic adversarial checks | Does not establish general prompt-injection resistance |
| 14 — documentation | Current README and this ledger describe supported behavior and limits | Historical documents remain historical; current behavior takes precedence |
